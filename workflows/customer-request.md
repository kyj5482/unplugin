# Workflow: 고객 요청 처리

트리거: 대표가 "고객 요청: ..." 입력, 또는 (향후) 고객 채널 접수.

```
고객 요청
   │
   ▼
[concierge] 접수 — flows/에 Flow 문서 생성, 요청 분류
   │
   ├─ 신규 고객인가? ──▶ [cs] 언플러그 타입 테스트+온보딩 확인(ops/survey.md) → 위임 1개 선정
   │
   ▼
[concierge] 위임 업무 실행 계획 수립 (필요시 [it] 브라우저 세션/도구 투입)
   │
   ▼
[it] 위임 업무 대행 실행 → 결과를 Flow에 기록
   │
   ▼
[product] 확보된 시간 추정 → 그 시간에 맞는 오프라인 경험 개인화 추천
   │
   ▼
[cs] 고객에게 결과 + 오프라인 추천 전달, 이후 피드백 수집(태깅 필수)
   │
   ▼
[concierge] Flow 완결 기록, 대표에게 요약 보고
   │
   └─ (피드백 수집 후) offline_story가 생생하면 ──▶ [marketing] 스토리 소재 브리핑
```

## 스트레스 케이스 분기 (환불·분쟁·해지·보증금)

접수 분류에서 스트레스 유형(`core/stress.py` 플레이북 10종)에 매칭되면 위 일반 흐름 대신:

```
[concierge/aru] 케이스 생성 (인텐트 추출: 상대·금액·주문번호) — 큐 최우선
   │
   ├─ email 채널 ──▶ [cs/rena] 상대방 이메일 협상 멀티라운드 (요구→재제시→통첩)
   ├─ portal 채널 ─▶ [it/bomi·dano] egolite 세션으로 해당 시스템 절차 수행 + 증빙
   │                  └─ 봇 차단 ──▶ [it/haru] 사람 개입 클릭 가이드 → hitl-done 보고로 재개
   ▼
[cs/tomi] 완료 추적 — 실제 입금 확인 전에는 완결 금지, 기한 초과 시 넛지·에스컬레이션 제안
   │
   ▼
입금 확인 → Flow 완결(증빙 포함) → 이후는 일반 흐름과 동일 (오프라인 추천 → 피드백)
```

## 규칙
- 위임 대행과 오프라인 추천은 **한 세트**다. 대행만 하고 끝내지 않는다.
- 스트레스 케이스는 "요청 접수"가 아니라 "결과(입금) 확인"이 완료 기준이다.
- 각 단계 완료 시 담당 부문이 Flow 문서의 해당 단계에 결과·시각을 기록한다.
- 막히면 Flow에 "확인 필요"로 남기고 대표에게 질문한다. 추측으로 진행하지 않는다.
