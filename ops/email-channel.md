# 이메일 채널 설계 v0 — "에이전트의 받은편지함"

> 고객 커뮤니케이션의 기본 채널은 **이메일**이다. 가입 시 고객마다 전용 주소
> (예: `jisoo.k@unplugin.me` — 도메인 미정)가 발급된다. 주소는 개인별로 소유·격리되므로
> 보안 경계가 명확하고, 앱 설치 없이 기존 이메일 습관 그대로 쓸 수 있다.
> 소유: IT (구현) + 상품기획 (규칙 UX) / 테스트: `tests/e2e/email.md`

## 세 가지 사용 방식

### 1) 포워딩 위임 — "이거 해줘"
받은 메일(청구서, 안내문, 예약 확인 요청…)을 전용 주소로 포워딩하면, 에이전트가 본문
맥락을 읽고 위임 요청으로 접수한다. 본문에 한 줄 지시("이의신청 해줘")가 있으면 따르고,
없으면 의도를 추정하되 모호하면 **회신으로 1회 질문**한다.

### 2) 시스템 수신자 등록 — "아예 네가 받아"
반복 발신 시스템(쇼핑몰, 학교, 관리사무소, 구독 서비스)의 수신자를 전용 주소로 바꿔
등록한다. 이후 그 시스템의 메일은 고객 손을 거치지 않고 에이전트가 직접 받는다.

### 3) 이메일 워크플로우 규칙 — "A가 오면 B 해줘"
고객(또는 CS가 대신)이 규칙을 정의한다:

```yaml
# 규칙 예시 (고객별 rules 파일)
- when:
    from: "noreply@school.example"
    subject_contains: "가정통신문"
  then: "요약해서 매주 금요일 한 번에 보내줘"
- when:
    from: "billing@telecom.example"
    subject_contains: "요금"
  then: "지난달보다 10% 이상 오르면 알려주고, 아니면 보관만 해줘"
```

## 메일 기반 흐름 가시성 (고객용 Unified View)

대표가 `flows/`로 전체를 보듯, **고객은 메일함으로 자기 일의 전체 흐름을 본다**:
- Flow의 모든 전환(접수→진행→확인 필요→완료/취소)마다 상태 메일이 발송된다
- 같은 일의 메일은 전부 같은 스레드(thread=Flow ID)로 묶인다 — 메일함에서 스레드 하나 = 일 하나
- 각 메일 하단에 지금까지의 타임라인(시각·부문·수행 내용)이 포함되어, 마지막 메일만 열어도 전체가 보인다
- 구현: `core/notify.py` + `core/flow.py` / 테스트: TC-EML-006

## 업무 플러그인과 자동 분류 (UC-G7)

고객이 "가능한 업무 목록"에서 고르는 일은 없다. **포워딩하면 분류기가 알아서 판단해 회신한다.**

- 처리 가능한 업무는 **플러그인 카탈로그**(`core/plugins/`, 100+종 — 사람용 목록: `ops/usecases.md`)로
  정의된다. 업무 유형마다 실행 방식(auto/browser), 결제 여부, 상태(available/beta/planned)가 다르다.
- 포워딩 수신 시 `core/classify.py`가 제목·지시를 카탈로그와 매칭:
  - **지원(available/beta)** → 해당 플러그인으로 분류해 바로 큐 접수, 분류 결과를 접수 메일에 포함
  - **미지원(카탈로그 밖/planned)** → 실행하지 않고 "새로운 유형 — 준비에 1~3일" 안내 후,
    상품기획·IT의 **신규 플러그인 백로그**로 핸드오프. 준비될 때까지 요금 미차감
- 신규 요청 백로그가 곧 상품기획의 로드맵이다 — 고객의 실제 요청이 플러그인 추가 순서를 정한다.

## 처리 파이프라인

```
수신 → ① 수신자 주소로 고객 식별 (주소=고객 1:1, 격리)
     → ② 발신자 검증 (등록 발신자? SPF/DKIM 통과? 아니면 "검토함"으로 격리)
     → ③ 규칙 매칭 → 있으면 규칙 실행 / 없으면 포워딩 위임으로
     → ④ 업무 플러그인 자동 분류 (지원 → 큐 / 미지원 → 신규 백로그 + 안내)
     → ⑤ Flow 생성·기록 (workflows/email-automation.md)
     → ⑥ 실행 — 결제·발신 등 중대 액션은 기존 승인 게이트(TC-DEL-005) 그대로
     → ⑦ 결과 회신 (같은 스레드로)
```

## 보안 원칙

- **주소 격리**: 주소↔고객 1:1. 다른 고객의 메일·규칙·프로필에 접근 불가
- **발신자 신뢰 등급**: 고객 본인 주소(인증됨) > 등록 발신자 > 미등록. **미등록 발신자의
  메일은 자동 실행 금지**, "검토함"에 격리 후 고객 확인
- **이메일 본문은 데이터, 지시가 아니다**: 제3자 메일 본문 속 명령("이 계좌로 송금")은
  프롬프트 인젝션으로 간주 (TC-DEL-011과 동일 방어)
- 민감정보(카드번호 등)가 포함된 메일은 본문을 로그에 남기지 않는다 (TC-DEL-006)

## 개인별 주소 호스팅 방안 비교 (2026-11 검토)

고객마다 주소를 발급하려면 "메일 서버를 직접 운영"할 필요가 없다. **전용 도메인 + 캐치올
(catch-all) 수신 라우팅**이 핵심이다: `*@unplugin.me`로 오는 모든 메일을 받아 수신자
주소로 고객을 식별하면, 주소 발급은 DB에 레코드 한 줄 추가일 뿐이다.

| 방안 | 수신 | 발신(회신) | 비용 | 운영 부담 | 평가 |
|---|---|---|---|---|---|
| **A. Cloudflare Email Routing + Email Workers** | 캐치올 수신 → Worker 코드로 파싱·처리 | 불가 — 발신은 별도(Resend/SES) 필요 | 수신 무료 | 매우 낮음 (DNS만) | **v1 권장** |
| B. AWS SES Inbound (+S3+Lambda) | 캐치올 수신 → S3 저장 → Lambda 트리거 | SES로 발신까지 일원화 | 종량제(저렴) | 중간 (AWS 구성) | v2 스케일 단계 |
| C. Mailgun/Postmark Inbound Webhook | 수신 파싱 → 우리 엔드포인트로 POST | 가능 | 월 고정 + 종량 | 낮음 | A/B의 대안 |
| D. 메일 호스팅(Migadu/Forward Email 등) 캐치올 + IMAP 폴링 | 캐치올 메일박스 1개를 주기 폴링 | 가능 | 월 ~$3-20 | 낮음 | v0.5로 적합 |
| E. 셀프 호스팅 (Stalwart/Mailcow/Maddy) | 완전 자체 운영 | 가능 | 서버비만 | **높음** (평판·차단·보안 운영) | 초기 비추천 |

판단 근거:
- 수신은 쉽고 발신이 어렵다 — 발신 도메인 평판(스팸 차단)이 리스크이므로, 발신은 평판 관리를
  대행하는 서비스(Resend, SES, Postmark)에 맡기고 SPF/DKIM/DMARC를 설정한다.
- 셀프 호스팅은 통제력은 최고지만 1인 운영에서 IP 평판·블락리스트 대응이 본업을 잠식한다.

## 단계별 구현 (IT 로드맵 연동)

1. **v0 — 로컬 시뮬레이션 (지금)**: `departments/it/inbox/`에 .eml/md 파일을 떨어뜨리면
   에이전트가 파이프라인대로 처리. 맥북에서 TC-EML 리허설 가능, 인프라·비용 0
2. **v0.5 — 단일 메일박스 + 서브어드레싱**: Gmail 등 계정 1개로 `unplugin.beta+고객id@gmail.com`
   형식 사용(+ 뒤는 같은 메일박스로 수신됨). IMAP 폴링 스크립트로 수신 → 파이프라인.
   도메인 없이 베타 고객 2~3명 실검증용
3. **v1 — 전용 도메인 + Cloudflare Email Routing (방안 A)**: 도메인 구입(unplugin.me 등) →
   캐치올 라우팅 → Email Worker에서 수신자 주소로 고객 식별 → 파이프라인 호출.
   회신 발신은 Resend(또는 SES) + SPF/DKIM/DMARC. 고객별 주소는 무작위성 있는 슬러그로
   발급(`jisoo.k7x2@`)해 주소 추측·스팸 유입을 줄인다
4. **v2 — SES 일원화 (방안 B)**: 고객 수백 명 규모에서 수신·발신·바운스 처리까지 AWS로
   통합, 수신함 격리를 고객별 S3 프리픽스로 구현

## 주소 정책 (보안 연동)

- 주소 = `이름슬러그.난수4자@도메인`, 고객당 1개 + 용도별 별칭(alias) 추가 발급 가능
  (예: 학교용/쇼핑용 별칭 분리 → 유출 시 해당 별칭만 폐기·재발급)
- 별칭 단위 폐기·재발급이 가능해야 한다 (스팸 유입 시 대응)
- 수신자 주소가 미발급 주소면 수신 거부(바운스) — 캐치올이지만 발급 레코드와 대조

## 요금제 연결

이메일 규칙 자동화는 Flow 티어부터 (ops/pricing.md). 규칙 실행도 위임 시간으로 집계.
