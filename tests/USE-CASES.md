# 고객 시나리오 유스케이스 인벤토리

고객 생애주기(유입 → 위임 → 오프라인 전환 → 피드백 → 확산) 순서로 정리한다.
각 UC는 하나 이상의 TC(tests/e2e/)로 커버되어야 한다. 매핑은 `TRACEABILITY.md`.

## A. 유입·온보딩 (ONB)

- **UC-A1** 신규 고객이 언플러그 타입 테스트+온보딩 확인(ops/survey.md)을 완료하고 첫 위임 1개를 선정한다
- **UC-A2** 고객이 온보딩을 중도 이탈했다가 재방문하면 이어서 진행한다
- **UC-A3** 고객이 "뺏기고 싶지 않은 활동"(Q4)으로 지정한 것은 어떤 경우에도 위임 제안되지 않는다
- **UC-A4** 고객이 한꺼번에 여러 업무 위임을 요구하면 한 가지부터 시작하도록 안내한다
- **UC-A5** 문진 결과가 고객 프로필로 저장되어 이후 모든 추천의 근거가 된다
- **UC-A6** 온보딩 미완료 고객이 바로 위임을 요청하면 필요한 최소 항목만 먼저 채우고 진행한다
- **UC-A7** 타입 판정 시 "비슷한 타입의 전환 사례"(위임 Top3·오프라인 사례·주당 시간)가 함께 제시된다

## B. 위임 실행 (DEL)

- **UC-B1** 반복 장보기/생필품 주문을 위임받아 완료한다 (정상 경로)
- **UC-B2** 예약(병원·식당 등) 위임 중 선택지가 생기면 고객 확인을 받고 진행한다
- **UC-B3** 가격 비교·탐색 위임은 요약된 선택지로 반환한다 (고객을 다시 스크롤로 끌어들이지 않는다)
- **UC-B4** 수행 불가 상황(사이트 장애, 재고 없음, 로그인 실패, CAPTCHA)에서 중단하고 상태를 통지한다
- **UC-B5** 결제가 필요한 지점에서는 반드시 멈추고 고객 승인을 받는다 (사전 승인 한도 포함)
- **UC-B6** 고객 계정·개인정보는 정해진 보안 원칙(최소 수집, 세션 격리, 기록 금지 항목)대로만 다룬다
- **UC-B7** 위임 범위 밖 요청(위험·불법·타인 권리 침해)은 거절하고 대안을 안내한다
- **UC-B8** 진행 중인 위임의 상태를 고객이 언제든 조회할 수 있다
- **UC-B9** 고객이 진행 중인 위임을 취소하면 안전하게 중단하고 중간 결과를 반환한다
- **UC-B10** 완료 보고에는 증빙(주문번호·영수증·스크린샷)이 첨부되고 요청 내용과 대조 검증된다
- **UC-B11** 수행 중 방문한 페이지의 악성 지시(프롬프트 인젝션)를 따르지 않는다
- **UC-B12** 로그인·결제정보 입력은 고객이 직접 하는 Takeover 모드로 넘기고 그동안 기록하지 않는다
- **UC-B13** 반복 위임은 회차마다 승인 게이트·알림·사용량 차감이 적용된 채 자동 실행된다

## C. 오프라인 전환 (OFF)

- **UC-C1** 위임 완료 시 확보된 시간을 추정하고, 감각 취향(Q6)·희망 활동(Q5)에 맞는 오프라인 경험을 추천한다
- **UC-C2** 고객이 추천을 거절하면 사유를 기록하고 다른 축의 대안을 재추천한다
- **UC-C3** 고객이 추천을 수락하면 해당 오프라인 경험의 예약까지 대행한다 (위임과 추천의 결합)
- **UC-C4** 2주 후 재문진으로 스크린타임 변화와 Reclaimed Hours를 실측한다

## D. 피드백·KPI (FBK)

- **UC-D1** 모든 위임 건에 대해 피드백이 표준 태깅(satisfaction, offline_realized, offline_story, reclaimed_hours)으로 수집된다
- **UC-D2** offline_realized=no 피드백은 원인이 분류되어 상품기획으로 핸드오프된다
- **UC-D3** flows/와 feedback/에서 Reclaimed Hours 깔때기(Delegated→Reclaimed)가 집계된다
- **UC-D4** 반복되는 불만은 담당 부문으로 개선 과제로 전환된다

## E. 마케팅 (MKT)

- **UC-E1** 생생한 offline_story가 3막 구조 초안이 되고, 대표 승인 후에만 게시된다
- **UC-E2** 실사용 데이터가 없으면 가상의 고객 스토리를 쓰지 않는다 (대표 베타 경험담으로 대체)
- **UC-E3** 게시물에서 고객 식별 정보가 익명화된다

## F. 대표 운영·과금 (OPS)

- **UC-F1** 대표 지시("지시: ...")가 담당 부문에서 처리되고 결과가 Flow와 함께 반환된다
- **UC-F2** 모든 업무(요청·지시)가 flows/에 단계·핸드오프·결과까지 빠짐없이 기록된다 (Unified View)
- **UC-F3** 동시 요청이 티어의 슬롯 수를 초과하면 큐에 쌓이고 대기 안내가 나간다
- **UC-F4** 큐 순서가 보장되고, 상위 티어는 더 많은 동시 슬롯을 갖는다
- **UC-F5** 고객의 해지·환불 요청이 규정대로 처리된다
- **UC-F6** 위임 시간 사용량이 티어 한도에 접근하면 사전 통지된다
- **UC-F7** 큐에서 장기 대기 중인 요청은 타임아웃 시 통지되고 고객이 대기/취소를 선택한다

## G. 이메일 채널 (EML) — 설계: ops/email-channel.md

- **UC-G1** 가입 시 고객별 전용 이메일 주소가 발급되고 고객 간 완전히 격리된다
- **UC-G2** 고객이 메일을 전용 주소로 포워딩하면 위임 요청으로 접수된다
- **UC-G3** 전용 주소를 수신자로 등록한 시스템의 메일은 규칙에 따라 자동 처리된다
- **UC-G4** "A가 오면 B 해줘" 규칙을 정의하면 조건 매칭 시 실행된다 (중대 액션은 승인 게이트 유지)
- **UC-G5** 미등록·사칭 발신자와 본문 속 명령(인젝션)은 자동 실행되지 않고 격리된다
- **UC-G6** 고객은 메일만으로 자기 일의 전체 흐름(접수→진행→완료)을 파악한다 — 전환마다 같은 스레드로 타임라인 포함 상태 메일
